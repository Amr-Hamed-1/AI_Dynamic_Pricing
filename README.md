# 🤖 Dynamic Pricing & Demand Forecasting Engine

An **end-to-end** machine learning & decision-optimization system that recommends profit-maximizing SKU prices based on competitor pricing, product category, and seasonality. It pairs an **economically constrained XGBoost demand forecaster** with a **vectorized price optimization engine**, exposed via **FastAPI** and an interactive **Streamlit** simulation dashboard.

> 🧪 Built on a **synthetic market simulator** with a known demand function — which makes it possible to measure the optimizer against *ground truth*, not just against its own model (see [Policy Backtest](#-policy-backtest--and-why-the-models-own-number-cant-be-trusted)).

---

## 📌 Business Problem & Two-Stage Solution

In e-commerce, static markups leave profit on the table: price too high and demand collapses; price too low and margin erodes. This system solves pricing in two stages:

1. **Demand Forecaster (`src/train.py`)**: Predicts monthly unit demand (`qty`) from competitor prices, relative price positioning (`price_ratio`, `price_diff_*`), product attributes, category, and seasonality — enforcing **monotonic price-elasticity constraints** (`monotone_constraints = -1`) so raising own price never spuriously increases predicted demand.
2. **Decision Optimizer (`src/optimization.py`)**: Evaluates 60 candidate prices around competitor pricing in a single vectorized batch call, computes expected `revenue = price × qty` and `profit = (price − cost) × qty`, selects the profit-maximizing price, and quantifies **Lift %** vs. keeping the current baseline price.

## 🧠 Technical Methodology & Leakage Guards

- **Strict Chronological Split (`temporal_train_test_split`)**: Splits strictly on `(year, month)` (`2017-01 .. 2018-07` for training, `2018-08 .. 2018-12` for testing) so zero future months leak into training while retaining a full seasonal cycle in-sample.
- **Post-Decision Leakage Prevention**: Contemporaneous outcome columns realized alongside `qty` (`customers`, `revenue`, `total_price`, `freight_price`) are strictly excluded from model features, and `PriceOptimizer` builds SKU context solely from historical training periods.
- **Time-Series Cross-Validation & Monotonicity**: `XGBRegressor` is trained on `log1p(qty)` (via `TransformedTargetRegressor`, predictions returned in units), tuned with `GridSearchCV` over 5-fold `TimeSeriesSplit`, with `monotone_constraints = -1` on `unit_price`, `price_ratio`, and `price_diff_1..3` to guarantee downward-sloping demand curves.

### 📊 Out-of-Time Forecasting Results (synthetic data — 4,800 rows: 3,800 train / 1,000 test)

| Model | MAE | RMSE | R² |
|---|---|---|---|
| RandomForest | 2.19 | 3.11 | 0.902 |
| **XGBoost (monotonic, log target)** | **1.70** | **2.35** | **0.944** |

> High R² is expected here: the synthetic demand is a known smooth function of the features plus 8% noise. On real data, expect substantially lower accuracy.

### 📈 Policy Backtest — and why the model's own number can't be trusted

`src/backtest.py` takes each SKU's last held-out month (`2018-08 .. 2018-12`), lets the optimizer pick a price, and scores that decision **two ways** (unit cost = 40% of competitor average price):

| Metric | Model-estimated *(circular)* | **Ground truth** |
|---|---|---|
| Portfolio profit lift vs. current price | +7.2% | **+0.7%** |
| SKUs improved | 99.0% | **61.0%** |
| Oracle ceiling (perfect pricing) | — | +1.2% |
| Share of achievable uplift captured | — | **56.7%** |

**Key finding — the optimizer's curse.** Scoring a decision with the same model that made it is circular: the argmax systematically picks prices where the model *over*-predicts demand, so model-estimated lift is inflated (~10× here). Because the data is synthetic, the true demand function is known (`generate_data.true_expected_demand`), so every recommendation is also re-scored against reality.

This check exposed a real bug in the first version: a raw-`qty` XGBoost had the right *average* elasticity (1.84 vs. true 1.80) but step-shaped local artifacts that the optimizer exploited — **−0.8% true profit** while claiming +8.3%. Training on `log1p(qty)` (natural for multiplicative, constant-elasticity demand) smoothed the price response and turned it into **+0.7%**, capturing 57% of the achievable uplift.

> The ceiling is small because with elasticity 1.8 the profit curve is flat near the optimum and current prices are already close to it — a realistic property of elastic markets.
>
> **Caveat:** the log-target fix was chosen after looking at this backtest, so the +0.7% is mildly optimistic. A fresh simulation seed / time window would be the clean confirmation.

### 🧪 From Backtest to Production

On real data there is no ground-truth demand function, so the only valid proof is a **controlled field A/B test**:

1. Randomly assign SKUs (stratified by category & volume) into **Treatment** (optimizer price) and **Control** (status-quo price).
2. Measure realized gross profit over a fixed window (e.g., 4 weeks) with guardrails (conversion rate, stockouts).
3. Roll out gradually only on statistically significant lift; add a price-change trust region (e.g. ±10%) to limit downside from model error.

## ⚠️ Honest Notes

- **Data is synthetic**, generated by `src/generate_data.py` with a known price-elasticity structure (elasticity = 1.8, Q4 seasonality, category effects). The schema mirrors the Kaggle *Retail Price Optimization* (Olist-derived) dataset explored in `notebooks/Cleaning&Eda.ipynb`, but the training pipeline has **not** been validated on that real dataset (it has only 676 rows).
- Cost per unit is assumed (40% of competitor average price); real COGS would replace it.

## 🔌 REST API Endpoints (`api.py`)

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/health` | Readiness & model load check |
| `GET` | `/products` | List available SKU identifiers |
| `GET` | `/model/info` | Model class, features, out-of-time metrics & monotonic constraints |
| `GET` | `/backtest/summary` | Aggregate out-of-time portfolio backtest KPIs |
| `POST` | `/optimize` | Compute optimal price, expected units, profit & baseline lift |

Example request:

```bash
curl -X POST http://localhost:8000/optimize \
  -H "Content-Type: application/json" \
  -d '{"product_id": "prod_0000", "competitor_price": 148.8, "product_cost": 50.0, "month": 11}'
```
